# Type coverage

One row per Arrow logical type, with the status of each dimension zarrow supports it in: building arrays,
validating them, the IPC format, the C data interface and the compute kernels. It is a status page, not a
roadmap.

## Evidence rule

Every claim cites its evidence, following the rule in [`CLAUDE.md`](../CLAUDE.md): a `yes` or `partial` row
names at least one source reference (path, colon, line of the implementing type or function) and at least one
test reference (path, colon, the exact test name in double quotes, or a `build.zig` step name).
`python -I tools/check_doc_evidence.py` checks that every reference resolves; CI runs it, and
`python -I tools/ecosystem_scorecard.py` counts the rows.

Per dimension:

- **yes**: the type is handled and a test exercises *that type* in *that dimension*. A test that only
  carries the type as a child of another type (for example bool inside a union) does not count.
- **partial**: the code path exists (usually a generic path shared with a tested type) but no test covers
  this type there, or the test covers only the schema / format string, or only zero-row data.
- **no**: not handled.

**Status** is the overall value: `yes` only if all five dimensions are `yes`, otherwise `partial` (or `no`
if every dimension is `no`). Dimension meaning:

| Dimension | Counts as tested when a test ... |
|---|---|
| Build | builds or reads an array of the type through its builder / array API |
| Validate | runs `validateLayout` or `validateFull` on an array of the type (accepting or rejecting it) |
| IPC | round-trips or reads record batches with rows of the type through the stream or file format |
| C ABI | exports or imports an array of the type through the C data interface (a format-only test is partial) |
| Compute | runs take, filter, concat or dictionary encode on an array of the type |

## Notes and gaps

- The per-type `yes` cells rest on `src/array/test_type_coverage.zig`. `buildSamples` builds one six-row
  array of every type in the table (the fixed-width aliases are listed in `fixed_width_cases`), with
  rows 1 and 4 null where the layout has a validity bitmap, plus int16 and int64 run-end variants. Each
  test loops over that explicit list:
  - Build: every fixed-width alias builder appends values and nulls, read back through `PrimitiveArray`.
  - Validate: `validateLayout` and `validateFull` accept each sample and a slice of it, and reject a
    copy with one corruption per layout (values buffer one byte short, last offset past the data or
    child, list-view sizes past the child, a view naming a missing data buffer, children that no longer
    cover the parent, a bad union type id or offset, a run end below the length, a dictionary index past
    the dictionary, a wrong null-type null count).
  - IPC: a batch of all samples and a batch of their slices round trip through the stream and the file
    format; every column passes `validateFull` and matches the source row by row.
  - C ABI: each sample and a slice of it are exported (schema and array) and imported; the imported
    type matches and every row matches.
  - Compute: `datumTake` (dense and nullable indices), `datumFilter` and `concatArrayRefs` on each
    sample and a slice, checked with the per-row oracle `rowsEqual` from `src/compute/test_datum.zig`.
- Parametric types are tested with one parameter set each (see the Notes column). Other units,
  precisions and widths share the same data path and differ only in metadata, which the IPC schema
  tests and the C data format tests cover.
- Bugs these tests found, fixed in the same change:
  - C data export of `string_view` / `binary_view` omitted the final buffer of variadic data-buffer
    sizes that the C Data Interface requires, and import kept that sizes buffer as a data buffer. Export
    now appends it and import drops it, so a view's buffer index must name a real data buffer
    (`src/ffi/c_data.zig:"c data import rejects a view whose buffer index names the variadic sizes buffer"`).
  - C data import expected three buffers for `list` / `large_list` and sized the third from the last
    offset; the C Data Interface has two (validity, offsets). Import now expects two; the offsets are
    bounded by the child in `validateLayout`.
  - C data import read a dictionary-encoded field (format = index type, `dictionary` set) as a plain
    integer column. The dictionary check now comes first, and import also bounds every non-null index by
    the imported dictionary
    (`src/ffi/c_data.zig:"c data dictionary field imports as dictionary and rejects indices past the dictionary"`).
    The IPC stream and file readers now do the same when a record batch (or a dictionary batch with
    nested dictionary columns) is decoded, rejecting the batch with `InvalidBody`
    (`src/ipc/stream_reader.zig:"stream and file readers reject a dictionary index equal to the dictionary length at decode"`).
  - The IPC writer ignored array offsets: a sliced column, or a dictionary delta (a slice of the grown
    dictionary), was written as the parent's first rows. The writer now rewrites any array with a nonzero
    offset in its tree at offset 0 (`concatArrayRefs`) before emitting buffers
    (`src/ipc/stream_writer.zig:"ipc writer emits dictionary delta on append-only dictionary growth"`
    now reads the delta back).
  - The IPC writer wrote null count 0 for a sliced null-type column; the reader rejected the batch. The
    writer now takes the count from `ArrayData.nullCount`.
- The arrow-testing file `at-0.14.1-generated_primitive_zerolength.arrow_file` (every integer, float,
  bool, binary, utf8 and fixed-size-binary column, zero rows) still covers the empty-buffer read path.
